# S3 — Do AI provenance marks survive common image, video and audio pipelines?

*EasyxLab · study S3 · October 2026 · status: working draft, not peer-reviewed*

**Paper:** [easybyte.es/lab/studies/s3/paper/](https://easybyte.es/lab/studies/s3/paper/) · [PDF](https://easybyte.es/lab/studies/s3/paper.pdf)

## Abstract

The EU AI Act (Art. 50(2)), California's AI Transparency Act (SB 942 as amended by AB 853) and China's GB 45438-2025 require synthetic media to carry machine-readable marks. The marks we test are: a C2PA manifest whose actions declare an IPTC `digitalSourceType` (`trainedAlgorithmicMedia`), the same IPTC term in XMP (`Iptc4xmpExt:DigitalSourceType`), and the `TC260:AIGC` XMP field that open-source implementations use for China's implicit label (its serialisation was not checked against the official text of GB 45438-2025). Invisible watermarks and fingerprints are out of scope.

We built a reproducible local lab: 23 synthetic fixtures (JPEG, PNG, WebP, MP4, M4A, WAV, MP3); the images come with each AI mark alone, all together or none. We ran seven of them (the three images with all marks plus a remote-manifest reference; MP4 and M4A with the XMP marks and C2PA; WAV and MP3 with C2PA only), signed with the c2patool test certificate, plus one public C2PA sample, through 41 transformations in Pillow, sharp/libvips (including a replica of the sharp call chain of the `next/image` optimizer), ImageMagick, ExifTool and ffmpeg, which gave 154 outputs and 474 output × mark observations.

**No pixel or container rewrite we tested kept an embedded C2PA manifest (0/124)**: re-saving, resizing or converting a signed image, video or audio file in Pillow, sharp, `next/image`, ImageMagick or ffmpeg removed the signed record every time, including every "keep metadata" option we tried. **Editing a single XMP field after signing left the manifest present but invalid (6/6).** The two XMP marks always shared the same fate. They survived only when the pipeline kept the XMP packet: by default in ImageMagick and ExifTool unless stripping, only with an explicit option in sharp or Pillow, never in `next/image`. No mark survived ffmpeg in any MP4/M4A/WAV/MP3 configuration tried (`-export_xmp 1` left an unreadable residue of the XMP marks). The only tested route to a valid credential on a derivative was re-signing after processing, with the original as an ingredient (4/4), and even then, in the three files that declared AI, the declaration survived only inside the ingredient, not in the new active manifest. CDN, platform and legal behaviour is reported from literal documentation quotes, kept separate from what we measured.

**Competing interests:** the authors' organisation develops ai-mark-lint, which automates the before/after comparison used here.

## Layout

| path | content |
|---|---|
| `METHOD.md` | corpus, pipelines, detection, classification rules |
| [paper](https://easybyte.es/lab/studies/s3/paper/) (web) | paper-style report |
| `scripts/run.sh` | one command: setup + corpus + all pipelines + matrix |
| `fixtures/` | reusable corpus (< 3 MB), documented in `fixtures/README.md` |
| `data/matrix.csv` | one row per output file × mark carried by its input |
| `data/summary.md`, `data/summary_compact.md` | generated pivots |
| `data/remote_followup.csv` | derivative vs original sidecar manifest |
| `data/versions.json` | exact tool versions of the last run |

## Run

```bash
brew install exiftool        # ffmpeg, python3 and node >= 18 must already be present
scripts/run.sh               # ~15 s; downloads c2patool 0.27.22, creates .venv and node_modules locally
                             # note: it regenerates fixtures/ too (new signatures, same classifications)
```

`.venv/`, `node_modules/`, `tools/` and `work/` are local-only (`.gitignore`). Nothing is uploaded anywhere. The only network access is downloading pinned tools and one public fixture from GitHub.
